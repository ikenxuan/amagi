## 调用形式与单次请求配置

Client 上的**绑定 Fetcher** 是 `client.<平台>.fetcher.<方法>(options, requestConfig?)`：cookie 已随 Client 绑好，第二个参数只作用于当前这一次调用，并与 Client 的实例级请求配置合并 —— 单次配置优先，`headers` 单独合并。

直接导出的**裸 Fetcher** 是 `<平台>Fetcher.<方法>(options, cookie?, requestConfig?)`：没有实例级配置，cookie 按次传，第三个参数直接作用于当前请求。`amagi.<平台>Fetcher` 与同名的命名导出（`import { bilibiliFetcher } from '@ikenxuan/amagi'`）是同一个对象。

两种形态都由端点注册表派生、走同一条执行管线、返回同一种信封，所以本页列出的方法名与参数对两者都成立。

### 用 `Cookie` 头覆盖单次调用的 cookie

`requestConfig.headers` 里**任意大小写**的 `Cookie`（`Cookie` / `cookie` / `COOKIE`）都会替换本次调用实际使用的 cookie：绑定形态覆盖 Client 上绑定的那份，裸 Fetcher 形态覆盖第二个参数。这次调用用哪份 Cookie，只写这一处就够。

</section>

## 读取返回值：取 `data`

方法永不抛异常，返回的是信封：成功支有 `data`，失败支有 `error`，两支都有 `message` 与 `meta`，顶层没有 `code`。本页所有示例统一用 `if (result.success)` 收窄之后再读 `result.data` —— 四种读法里只有它既不必额外 import，收窄后的 `data` 又不带 `| undefined`：

| 读法                            | 拿到的 `data`                       |
| ------------------------------- | ----------------------------------- |
| `if (result.success)`           | `T`（本页示例统一用这种）           |
| 直接读 `result.data`（不收窄）  | `T \| undefined`                    |
| `list.filter(isSuccess)`        | `T`（数组回调里没有 `if` 可用）     |
| `unwrap(result)`                | `T`，失败时抛 `AmagiThrownError`    |

四种读法的完整说明、失败分支的字段与三条逃生舱见[响应类型](/docs/v7/usage/guide/type-mode)。

### 大整数 ID 与响应类型

默认 JSON 解析会把超出 JavaScript 安全整数范围的裸整数保留为十进制字符串，防止直播间、作品等 ID 被四舍五入。普通安全整数、浮点数和指数写法保持原样；显式文本响应和自定义 `transformResponse` 仍由调用方控制。响应 ID 的类型因此可能是 `string | number`，需要统一存储时可用 `String(id)`；不要先调用 `Number()` 再拼接请求。

新增端点只声明已有证据支持的响应字段；缺少完整成功响应样本的字段使用 `unknown`，使用前应检查对象、数组或字符串等实际结构。

</section>

<section id="preamble-xiaohongshu">

已收录的端点在未提供 Cookie 时会初始化游客会话，并沿用当前请求的 User-Agent 和传输配置。同一客户端、UA 和请求配置下复用五分钟，并合并并发初始化；初始化失败后，下一次调用可以重试。不同客户端、代理、请求头或适配器等配置分别缓存；裸 Fetcher 也按其请求配置隔离。游客会话只能访问上游允许匿名读取的数据，需要登录的内容仍须传入有效登录 Cookie。

显式传入 `web_session` 或 `userId` 时，请保留与它配套的 `a1`。缺少 `a1` 会返回 `error.kind: 'auth'`、`error.code: 'COOKIE_MISSING'`，并且不发送请求。`client.xiaohongshu.request` 自定义请求不执行端点的游客初始化，调用方仍需提供有效的 `a1`。

## 本页之外：自定义请求

本页是已收录的端点方法。要请求 amagi 尚未收录的快手接口，用 `client.kuaishou.request`（默认签名器 `hxfalcon`）。快手那份 `apiUrls` **返回的不是 URL 字符串**，而是请求描述对象，对应关系是 `url` → 第一参、`body` → `config.data`、`signPath` → `amagi.signPath`：

```ts twoslash
import amagi from '@ikenxuan/amagi'
const client = amagi({ cookies: { kuaishou: 'did=xxx' } })
// ---cut---
// H5 那份（videoWork / videoWorkFull / comments）：requiresSign 是必填布尔
const d = client.kuaishou.apiUrls.videoWork({ photoId: '3xqxxxx' })
const r = await client.kuaishou.request.request({
  method: d.method,
  url: d.url,
  data: d.body,
  headers: { Referer: d.referer },
  amagi: { sign: d.requiresSign ? 'hxfalcon' : false, signPath: d.signPath }
})
```

**`live_api` 那批不能照抄这段**：它们的 `requiresSign` 是**可选**的（缺席不代表免签），也没有 `referer` 字段。要签就**不给 `sign`**（走平台默认 `'hxfalcon'`）或显式写 `'hxfalcon'`：

```ts twoslash
import amagi from '@ikenxuan/amagi'
const client = amagi({ cookies: { kuaishou: 'did=xxx' } })
// ---cut---
const d = client.kuaishou.apiUrls.userInfoById({ principalId: 'KPL704668133' })
const r = await client.kuaishou.request.request({
  method: d.method,
  url: d.url,
  amagi: { signPath: d.signPath }
})
```

详见[自定义请求](/docs/v7/usage/advanced/custom-request)。

</section>

<section id="note-bilibili-comments">

`type` 是评论区类型：1=视频、11=图文动态、12=专栏、14=音频、17=文字动态；端点声明只接受 v6 的那批取值（1、2、4–22、33），其余直接判参数校验失败。

<section id="note-bilibili-userLiveStatus">

直接读直播状态，不依赖用户空间动态里的直播推荐卡片，适合轮询开播状态。返回里主要看这几个字段：

| 字段         | 说明                              |
| ------------ | --------------------------------- |
| `roomStatus` | `1` 已开通直播间，`0` 未开通      |
| `liveStatus` | `1` 正在直播，`0` 当前未开播      |
| `roomid`     | 直播间 ID；未开通直播间时为 `0`   |
| `title`      | 直播间标题                        |
| `cover`      | 直播封面                          |

</section>

<section id="note-bilibili-bangumiInfo">

`ep_id` 与 `season_id` **二选一**：两个都是可选参数，但端点声明的 `refine` 要求至少给一个（都不给会以参数校验失败返回）。ID 带不带 `ep` / `ss` 前缀都行，`build` 会削掉。

</section>

<section id="note-douyin-parseWork">

推荐用 `parseWork`：它自动识别作品类型（视频 / 图集 / 合辑）并返回对应数据，不必先猜类型再挑方法。

<section id="note-kuaishou-userWorkList">

v6 的 `count` / `pcursor` 已被 `number` + 声明式翻页取代：调用方只说明要多少条，`pcursor` 游标的带入与停止条件由端点声明的 `paginate` 处理。

</section>

<section id="note-xiaohongshu-noteDetail">

`xsec_token` 可以从笔记的分享链接里取，形如 `xsec_xxx`。

</section>

<section id="note-xiaohongshu-noteComments">

v6 的 `cursor` 参数已由声明式翻页接管（小红书的 string 游标与抖音的 number 游标，语义差异收敛在端点声明里），调用方只说明要多少条。

</section>

<section id="note-xiaohongshu-searchNotes">

可传 `sort`（`general` / `popularity_descending` / `time_descending`）与 `note_type`（0 全部、1 视频、2 图文）。接口使用手动页码 `page`；同一轮搜索翻页时，复用 `search_id` 与 `session_id`，每页的请求标识由 SDK 自动生成。

```ts verify
import amagi, { xiaohongshuUtils } from '@ikenxuan/amagi'
const client = amagi({ cookies: { xiaohongshu: 'a1=...' } })
const search = {
  keyword: '旅行',
  search_id: xiaohongshuUtils.sign.getSearchId(),
  session_id: xiaohongshuUtils.sign.getSearchSessionId()
}
const firstPage = await client.xiaohongshu.fetcher.searchNotes({ ...search, page: 1 })
const secondPage = await client.xiaohongshu.fetcher.searchNotes({ ...search, page: 2 })
```

</section>

<section id="note-douyin-mixAweme">

`mix_id` 是合集 ID，不是单条作品的 `aweme_id`。v7 用 `number` 表示目标条数，内部每页最多请求 20 条，并按上游 `cursor` 自动翻页（游标由端点接管，不在调用方签名里）。聚合后的 `aweme_list` 包含本次收集到的作品，游标与其他元数据取最后一页。

</section>

<section id="note-xiaohongshu-searchUser">

公开方法名是 `searchUser`，与 `searchNotes` 一致。支持关键词或小红书号查询，手动传 `page` / `page_size` 翻页。该接口的 `code: 1000` 只有同时出现 `success: true` 时才作为成功处理，其他接口沿用各自的业务码判定。

</section>

<section id="note-xiaohongshu-searchHotList">

无业务参数，可调用 `client.xiaohongshu.fetcher.fetchSearchHotList()`。返回上游当前热榜；没有完整录制证据的条目字段保留为 `unknown`，使用前应自行收窄。

</section>

<section id="note-xiaohongshu-subComments">

`root_comment_id` 是要展开的一级评论 ID，`note_id` 与 `xsec_token` 来自同一篇笔记。传入 `number` 指定目标回复数，SDK 每页最多请求 10 条并自动推进游标。无需传 v6 补丁里的 `num` 或 `cursor`。

</section>

<section id="note-xiaohongshu-liveRoom">

`room_id` 使用字符串，避免 JavaScript 大整数精度丢失。默认 `variant: 'web'`，`request_user_id` 可显式传入，也可从 Cookie 的 `userId` 读取；`variant: 'h5'` 不使用这个参数。两种接口的返回字段可能不同，协议类型只声明已有证据支持的共同字段。

</section>

<section id="note-xiaohongshu-liveStatus">

传入字符串 `room_id` 查询直播状态，默认 `scene: 'share_out_of_app'`。是否在播需读取上游返回的状态字段；HTTP 请求成功本身不代表直播正在进行。

</section>

<section id="note-xiaohongshu-liveSquare">

无必填参数，默认获取 27 条推荐直播间。需要翻页时手动传入上游返回的 `cursor_score`；它不是 v7 的 `number` 自动分页端点。`extra_info` 在 SDK 中可传对象，通过 HTTP query 调用时可传 URL 编码后的 JSON 对象字符串。

</section>

<section id="note-xiaohongshu-userProfile">

用户资料改用 JSON 接口，平台响应包含 `data.basic_info`、`data.interactions` 与 `data.tab_public`。SDK 的 `result.data` 是这份原始响应，所以资料位于 `result.data.data`。读取旧主页 HTML 初始状态路径的调用方需相应调整。

```ts verify
import amagi from '@ikenxuan/amagi'
const client = amagi({ cookies: { xiaohongshu: 'a1=...' } })
// ---cut---
const result = await client.xiaohongshu.fetcher.fetchUserProfile({ user_id: 'user-id' })
if (result.success) {
  const profile = result.data.data
  const nickname = profile?.basic_info?.nickname
  if (typeof nickname === 'string') console.log(nickname)
  console.log(profile?.interactions, profile?.tab_public)
}
```

这些字段目前是可选协议字段，未确认的内部结构保持 `unknown`；应像上例一样检查后再使用。

</section>

<section id="note-xiaohongshu-userNoteList">

用户主页签发的 `xsec_token` 仍为必填，并与 `xsec_source` 一起传给上游。不要将笔记详情的 token 当作用户主页 token 使用。

## v6 的 passport 四方法

`requestPassportQrcode` / `checkPassportQrcode` / `sendPassportVerifyCode` / `validatePassportVerifyCode` 仍在裸 Fetcher（`douyinFetcher`）上，且都标了 `@deprecated`。它们是**会话**而不是端点 —— 不在端点注册表里，也不在 `client.douyin.fetcher` 上，所以本页（由注册表派生）不列它们。

新代码请走 v7 的登录会话：`client.douyin.login.qrcode()` 新建一次扫码会话，`client.douyin.login.resume(blob)` 从 `serialize()` 的产物恢复；轮询、退避、超时、二次验证编排都由引擎负责，不用自己拼 passport 的取码与轮询。会话的每一步还会发到实例总线上（`session:state` / `session:success` / `session:error`），见[事件系统](/docs/v7/usage/advanced/events)与[项目架构](/docs/v7/dev/architecture)的「会话（登录）」一节。

<Callout type="warn">
  两条路径的事件总线不是同一条：passport 四方法写的是 **v6 全局单例**
  `amagiEvents`（`api:*` / `log:debug`），`client.douyin.login` 写的是**实例总线**
  `client.events`（`session:*`）。
</Callout>
