# 贡献指南

感谢你对 amagi 的贡献！本文档介绍提交规范和 PR 流程。

## 提交规范

使用 [Conventional Commits](https://www.conventionalcommits.org/) 规范。**允许的类型由 `.release-please-config.json` 的 `changelog-sections` 定义**，`commit-msg` 钩子读同一份配置校验 —— 类型写错提交会被直接拒掉。当前九种：

| 类型       | 说明      | 示例                                |
| ---------- | --------- | ----------------------------------- |
| `feat`     | 新功能    | `feat: add fetchVideoTags API`      |
| `fix`      | Bug 修复  | `fix: correct parameter validation` |
| `perf`     | 性能优化  | `perf: cache wbi keys`              |
| `revert`   | 回滚      | `revert: feat: add fetchVideoTags`  |
| `docs`     | 文档更新  | `docs: update installation guide`   |
| `style`    | 代码风格  | `style: reformat sign helpers`      |
| `chore`    | 构建/工具 | `chore: update dependencies`        |
| `refactor` | 重构      | `refactor: simplify fetcher logic`  |
| `test`     | 测试      | `test: add unit tests for sign`     |

<Callout type="warn">
  钩子的校验正则是 `^(类型)(\(域\))?:`，**不接受 breaking 标记 `!`** —— `feat!:` 与 `feat(scope)!:`
  都会被拒。破坏性变更请把 `BREAKING CHANGE:` 写在提交信息的 body 里。
</Callout>

Merge / Revert / Initial commit 这类 Git 自动生成的信息在豁免名单里，不受类型校验约束。

### 提交信息格式

```
<type>(<scope>): <subject>

<body>

<footer>
```

示例：

```
feat(bilibili): add fetchVideoTags API

- Add VideoTagsParams type
- Add validation schema
- Implement fetcher method

Closes #123
```

## 发起 PR

<Steps>
<Step>
### 同步上游

确保你的 Fork 是最新的：

```bash
# 添加上游仓库（只需一次）
git remote add upstream https://github.com/ikenxuan/amagi.git

# 同步上游
git fetch upstream
git checkout main
git merge upstream/main
```

</Step>

<Step>
### 创建分支

从最新的 `main` 分支创建功能分支：

```bash
git checkout -b feat/your-feature
```

分支命名规范：

- `feat/xxx` - 新功能
- `fix/xxx` - Bug 修复
- `docs/xxx` - 文档更新
- `refactor/xxx` - 重构

</Step>

<Step>
### 开发与提交

```bash
# 开发...

# 提交
git add .
git commit -m "feat: your feature description"
```

</Step>

<Step>
### 推送到你的仓库

```bash
git push origin feat/your-feature
```

</Step>

<Step>
### 创建 Pull Request

1. 在 GitHub 上打开你的 Fork 仓库
2. 点击 "Compare & pull request"
3. 填写 PR 描述：
   - 说明改动内容
   - 关联相关 Issue（如有）
   - 列出测试情况
4. 提交 PR 到 `ikenxuan/amagi` 的 `main` 分支
</Step>
</Steps>

## 代码风格

### 基本规范

- 使用 TypeScript 严格模式
- 使用 Oxlint 进行代码检查
- 运行 `pnpm fix` 自动修复格式问题

### 导入顺序

导入顺序**不用手排**：`pnpm fix` 会跑 oxfmt，`sortImports`（`oxfmt.config.ts`）
按两组整理 —— 先是裸包名（外部依赖），空一行，然后是相对路径，各组内按路径字典序。
`import type` **不单独成组**，它按自己的路径排进相对路径那一组：

<include lang="ts" meta='title="packages/core/src/platforms/bilibili/endpoints/comments.ts"'>../../../../../core/src/platforms/bilibili/endpoints/comments.ts#docs-import-order</include>

（这段不是抄的，是 `packages/core/src/platforms/bilibili/endpoints/comments.ts` 的开头
本身 —— 之前那份手抄版本就烂过一次：它停在三条 import，而真文件早就多了
`type PaginatedValue` 一行、`defineEndpoint` 后面多了 `type`、`bilibiliApiUrls`
后面多了 `type CommentType`。所以别写「外部 / 内部 / 类型」三组 —— 排出来不是那个样子，
提交前跑一次 `pnpm fix` 就会被改回去。看第二组四行：两条 `import type`
（`runtime/paginate`、`types/ReturnDataType/Bilibili`）没有被拎出来单独成组，而是
夹在 `contracts/endpoint` 与 `../api` 两条值导入之间，各按自己的路径字典序落位 ——
`contracts` < `runtime` < `types`，而 `../../../*` 整体排在 `../api` 前面。）

### 注释规范

函数和接口需要 JSDoc 注释：

```ts twoslash
/**

 */

  // ...
}
```

## 响应样本（fixtures）要提交进 git

`packages/core/test/fixtures/<平台>/` 放的是**脱敏后的真实响应**。它们是响应类型的证据，
按下面这条策略管理：

- **提交进 git，但只提交脱敏后的精简代表** —— 每个变体留 1~3 份就够，不要把全量样本
  都塞进来。实测参照：快手第一批 6 份合计 **60 KB**，按这个密度铺满 61 个端点大约
  1~2 MB，可以接受。
- **不提交就等于放弃 `--check`**。类型将来是样本的纯函数（`pnpm gen:types`），而
  `--check` 要在 CI 里从样本重新生成一遍再逐字节比对 —— 样本不在仓库里，CI 就只能校验
  「类型没被手改」，没法校验「类型与证据一致」，那和现在没有区别。这是这条策略的**主要**
  理由，体积只是次要考量。
- **全量样本留本地**，别提交。它们对采样统计有用（「237 条评论里 1 条带 attachments」
  这类结论要靠量），但进仓库只会让 diff 没法 review。

<Callout type="warn">
  脱敏不是「把值改乱」。两条规则省了样本就没用甚至有害：**同一真值换成同一假值**
  （不然分组、引用这类关系会被打散，断言反而假绿）、**位数与字符集与真值同形**
  （位数变了会顺手改掉「大整数超 `MAX_SAFE_INTEGER` 会掉精度」这类形状，
  而那正是类型要描述的东西）。结构与字段名一字不改，只换值。
  做法与踩过的点见 `test/platforms/kuaishou/fixtures.test.ts` 的文件头。

  手工脱敏现在有了对应的实现：`packages/typegen` 的 `scrubSample`。它把上面两条做成了
  规则，假值一律从原值哈希派生（同一份响应重录一遍产出逐字节相同的文件），
  超界整数换完仍然超界，而替换清单里**连原值的哈希都不留** —— 清单要跟样本一起提交，
  短值的截断哈希是可以爆破的。
</Callout>

## `.doc.json`：注释与形状分开存

生成的响应类型是**样本的纯函数**，所以往产物里手写注释等于白写 —— 下次
`pnpm gen:types` 就冲掉了。语义要写在 sidecar 里：

```json title="corpus/bilibili/userDynamicList.doc.json"
{
  "$comment": "JSON 没有注释，说明写这里。paths 的键是字段路径，值是要生成的 JSDoc",
  "discriminantPath": "data.item.type",
  "paths": {
    "": "一条动态。按 `data.item.type` 分成六支，收窄请用 `guards.ts` 里的 `is*`",
    "data.item.type": "动态类型（判别式）。它决定 `modules` 下有哪些键",
    "data.item.modules.module_author.mid": "作者 UID。与 `params.uid` 是同一个人"
  }
}
```

三条要点：

- **路径写法**与仓库其它地方一致：根是空串，对象键用 `.` 连，跨数组加 `[]`
  （`data.items[].id`）。空串那条注释挂在根类型上。
- **孤立 pointer 会被报出来**。指向已经不存在的路径，意味着那个字段被删了或改名了 ——
  而那正是注释开始说谎的时刻，所以它是告警而不是静默忽略。
- **共用类型上只能挂一份注释**。结构等价的子树共用一个类型（不然加一条注释就多出一份
  重复类型，人就不敢写注释了），所以两条不同的注释指向同一个位置时，第二条挂不上去并
  报 `conflict`。要么把两处写成同一句，要么让形状真的不一样。

`discriminantPath` 是可选的逃生口：欠采样时自动发现可能挑错判别式（每个变体只有一份样本时，
`id_str` 这种字段与真判别式完全同分），补样本是正解，但在补齐之前可以在这里把结论钉死。
填 `false` 表示这个端点不要判别联合。

## PR 检查清单

提交 PR 前，请确认：

- [ ] 类型检查通过（`pnpm typecheck`）
- [ ] lint 通过（`pnpm lint`）
- [ ] 单元测试通过（`pnpm test`）
- [ ] **类型测试通过（`pnpm test:types`）** —— `tsconfig` 的 `exclude` 不检查 `**/*.test.ts`，测试文件里的类型错误只有它能抓到
- [ ] OpenAPI 产物一致（`pnpm openapi:check`）—— 改了端点就要跑 `pnpm openapi` 重新生成并提交，**不要手改 `openapi.json`**
- [ ] 无循环依赖（`pnpm deps:check`）
- [ ] 响应类型体积在预算内（`pnpm types:size`）—— 超了先确认是不是意外膨胀
- [ ] 构建成功（`pnpm build`）
- [ ] 改了响应类型的话，样本也留了（见上一节）
- [ ] 已手动测试新功能
- [ ] 提交信息符合规范
- [ ] PR 描述清晰完整

<Callout type="info">
  这份清单与 CI 的质量门禁 job 是同一套检查（`.github/workflows/release.yml`）。
  本地全绿基本等于 CI 全绿 —— 唯一的例外是文档站整站构建（`pnpm build:docs`），
  它最容易被本地环境挡住。
</Callout>
