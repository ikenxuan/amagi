# 传输与签名

**全仓只有 `transport/` 能发请求。** 这是一条架构约束，不是习惯 —— 端点需要发请求（换游客 cookie、取 wbi key）只能通过 `ctx.send`，由 transport 注入。v6 里签名模块绕过统一入口直连 axios 的问题，在 v7 的结构下不再可能发生。

## HttpClient.send 做的事

一次 `send` 的内部顺序：

1. **构造 axios 配置** —— header 合并顺序是 **平台基线 → 实例 `requestConfig.headers` → 单次 `perCall.headers` → `spec.headers`**，每次都从输入重建 `AmagiHeaders`（大小写不敏感）。合并完再按 `spec.dropHeaders` 删头（见下）。UA 原样发出、不改写：a_bogus 的 UA 摘要、`sec-ch-ua` 品牌、抖音 `browser_name` 与小红书 webprofile 指纹都按同一个 UA 计算（2026-10-07 前这里会剥掉 `Edg/x.y`，签名用的却是原 UA）。
2. **登记 trace 并计数** —— `tracer.begin(...)`，`meta.attempts` 恒等于登记条数。这一步与 `debug` 无关。
3. **发 `http:request` 事件**（装了总线时）。
4. **`axios(config)`**。
5. **成功** → 发 `http:response`，非 2xx 再补一条 `http:error`，返回 `RawResponse`。

`RawResponse` 带 `status` / `statusText` / `headers`（`AmagiHeaders`）/ `setCookie`（**原始数组**）/ `body` / `durationMs` / `url`。

<Callout type="info">
  **刻意不设 `validateStatus`。** 于是非 2xx 走 axios 的失败分支，由 transport 自己决定是不是重试。
  这与 v6 的 `transport/legacy.ts` 相反 —— 那里是 `validateStatus: () => true`，什么状态码都算成功。
</Callout>

## `client.<平台>.request`：第二个入口，同一条管线

`client.<平台>.request`（[自定义请求](/docs/v7/usage/advanced/custom-request)）是 fetcher 之外的第二个发请求入口，但它**不新开执行路径**：axios 归一化后的配置被翻成 `RequestSpec`，现场合成一个一次性的 `EndpointDef`（`client/request/adapter.ts` 的 `makeRequestDef`），再交给同一个 `callEndpoint`。于是下面这些一样都不用重写：

| 管线提供的东西 | 在 request 这条路上的形态 |
| -------------- | -------------------------- |
| judge | 平台默认判定表（合成声明不带端点级 judge） |
| 信封 | 同一套 `AmagiResult`，成功 / 失败两支的字段一致 |
| 退避重试 | 平台档案的 `retryOn`；抖音另开 `retryFresh`，重试时重新签名生成新的 `msToken` + `a_bogus` |
| observe | 抖音回收 `webid` 的钩子照跑 —— adapter 只包一层，不替换 |
| ensureCookie | 抖音的 cookie 审计照跑 —— 缺访客 id 时先铸造再发主请求 |
| 事件 / trace | 与端点同一条线（`http:*` / `network:*` / `api:*`） |

代价是它继承了「端点」这个形状：`params` 是空对象（没有参数校验）、没有 `decode` / `normalize` / `paginate`。

两处「axios 语义 → amagi 语义」的转换都在 adapter 里：

- **`toRequestConfig`** 把配置翻给 transport，其中十三个键**不往下传**（`NOT_FORWARDED_KEYS`）：`url` / `method` / `data` 已经进了 `RequestSpec`；`params` / `paramsSerializer` / `baseURL` 已经被 `instance.getUri(config)` 拼进 URL，再传一遍会被内层 axios 拼第二次（`?a=1?a=1`、`baseURL` 双前缀）；`headers` 改从 `requestConfig.headers` 走（签名读的就是它 —— 抖音的 `a_bogus` 用 `ctx.userAgent`）；`adapter` 传下去会在**内层**覆盖掉签名与信封；`transformRequest` / `transformResponse` 漏下去会让 body 永远不序列化；`validateStatus` 下去会与 judge 打架；`responseType` 进 `spec.responseType`，`amagi` 是给 adapter 自己看的。
- **`toAxiosResponse`** 把信封包成 `AxiosResponse`。这个 adapter **恒 resolve** —— axios 的 `settle` 只在内置 adapter 里，自定义函数 adapter 的返回值不经状态校验。所以「失败抛不抛」是 `client/request/index.ts` 按**信封**决定的，与 HTTP 状态码无关；没拿到响应时 `status` 是哨兵 `0`，`AxiosError.response` 留空而不是编一个假的。

自己直接调 `HttpClient.send` 会把上面这一整列**全部**丢掉，且与端点行为分叉 —— 这就是 adapter 存在的理由。

## 抖音的 cookie 审计：缺访客 id 时自动铸造

受 secsdk 保护的端点（`/aweme/v1/web/music/detail/` 等 14 条 GET）要求 cookie 里带访客 id（`UIFID` 家族），而它**不由登录颁发**——passport 扫码链路只发身份 cookie。缺了它，这些端点稳定回 `403 Blocked by ArgusSecurityPlugin Uifid Not Found`（判 `SIGNATURE_REFUSED`）。

`PLATFORM_RUNTIME.douyin.ensureCookie` 让这件事自愈：每次调用在 prepare 之后、build/sign 之前审计一次 cookie，缺访客 id 就**纯 HTTP 铸造**一个并合并。铸造链路（线上实测）：

1. `GET www.douyin.com`（无 cookie）→ 服务端在 Set-Cookie 里发 `__ac_nonce`。响应体是一份 VMP 挑战页，**不读**；
2. 用 `sign/acSignature.ts` 的 `computeAcSignature` **纯算**出 `__ac_signature`（47 字符，`_02B4Z6wo00f01` 开头）—— 四则运算加字符串拼接，不执行挑战页里的任何脚本；
3. 带 `__ac_nonce + __ac_signature` 再 GET 一次 → 服务端一次性 Set-Cookie：`ttwid` + `enter_pc_once` + `web_sign_token` + `UIFID_TEMP`。`UIFID_TEMP` 的有效期没测过；同一 IP + UA 重复铸造每次拿到的值都不同（2026-10-11 实测）。

三个设计要点：

- **挑战页不解析、不执行**——签名算法已从 JSVMP 字节码里 lift 出来写成纯函数，`MintDeps.getHome` 的返回类型只有 `{ setCookies }`，于是「解析挑战页」在类型上就做不到。代价是抖音换算法不再自动跟随：换版的表现是服务端不认签名、第二发拿不到 `ttwid` / `UIFID_TEMP`，按铸造失败走 ttwid 回落，**没有 vm 回落**。
- **审计永不为调用增加失败**——网络失败、形状变化、签名被拒，一律原样返回，请求按既有路径走（该 `SIGNATURE_REFUSED` 还是它）；实现里不抛错，execute 也不包一层。
- **只补缺失的名字**——已有 `ttwid` 的登录态只追加 `UIFID_TEMP`，不动调用方的设备标识；进程级缓存（key = cookie + UA）让同一 cookie 只铸一次，不设过期，只有铸造成功的结果进缓存（ttwid 回落刻意不进）。

登录完成时（`session/qrcode.ts`）也审计一遍，扫码登录直接产出带访客 id 的凭证。零配置（cookie 都没配）时审计会铸造完整访客 cookie——全新部署的第一次请求就是可用的。测试环境（vitest）默认出口**不出网**，要测铸造就注入 `MintDeps.getHome`（`mint.test.ts` 全部走注入，喂的是 Set-Cookie 行数组——签名纯算之后铸造链路不碰响应体，用不上挑战页 fixture；纯算实现本身由 `ac-signature.test.ts` 拿真实挑战页做 oracle 比对）。 铸造是 amagi 自主发起的出网请求，**有权拒绝**：设 `AMAGI_DISABLE_DOUYIN_MINT=1` 关闭（cookie 保持原样，受保护端点按 `SIGNATURE_REFUSED` 归因失败）。

## `spec.dropHeaders`：端点也能删基线头

`spec.headers` 只能**覆盖**同名头，给不出「这个端点不该发某个基线头」。快手 H5 端点撞上了这个缺口：平台基线是照桌面 Chrome 攒的（`origin` / `sec-ch-ua*` / `sec-fetch-*`），而 H5 端点用移动 UA —— 拼在一起发出去的请求自我矛盾（UA 说 iPhone Safari，客户端提示说 Chrome 142 / Windows，而 Safari 根本不发 `sec-ch-ua`）。

`dropHeaders` 在所有 merge 之后执行，所以**同时出现在 `headers` 与 `dropHeaders` 里的头会被删掉** —— 端点自己要发的头别写进清单。快手那份清单是 `platforms/kuaishou/config.ts` 的 `KUAISHOU_H5_DROP_HEADERS`。

<Callout type="warn">
  如实记账：这条能力不是为了修某个风控。`photo/info` 的 `2001` 在剥到只剩 6 个头之后仍然复现 —— 改它的理由只是「发出去的请求不该自我矛盾」。
</Callout>

## 失败分支的三条路

拿到 `AxiosError` 后先问 `decideRetry`：

| 判定 | 有响应？ | 行为 |
| ---- | -------- | ---- |
| 不重试 | 有 | 走正常返回路径，状态码原样带出（交给 judge 去判） |
| 不重试 | 无 | 发 `http:response` + `network:error`，**抛 `TransportError`** |
| 重试 | — | 发 `http:response`（+ 非 2xx 时 `http:error`）+ `network:retry`，`await sleep(delayMs)` 后继续 |

非 `AxiosError` 的抛出物原样上抛，由 `execute` 的唯一 catch 归到 `internal`。

## 重试策略

策略是纯函数模块，可以单独读、单独测：

| 常量 / 函数 | 值 / 行为 |
| ----------- | --------- |
| 可恢复 errno 白名单 | 9 个（`ECONNRESET` / `ETIMEDOUT` / `ENOTFOUND` 等） |
| `DEFAULT_MAX_RETRIES` | 3 |
| `RETRY_DELAY_BASE_MS` | 1000 |
| `backoffDelayMs(attempt)` | `base × 2^(attempt-1)` → 1s / 2s / 4s |
| `isRetryableStatus` | **429 与 ≥500** |
| `retryReasonCode` | `ETIMEDOUT` → `TIMEOUT`；其他可恢复 errno → `NETWORK_ERROR`；429 → `RATE_LIMITED`；5xx → `PLATFORM_UNAVAILABLE` |

超时没有 transport 自己的实现，靠 axios 的 `timeout`。四个平台的 `config.ts` 给的默认值是 10000ms，调用方的 `request.timeout` 可以覆盖。超时归因看 errno：`ETIMEDOUT` / `ECONNABORTED` → `kind: 'timeout'` / `code: 'TIMEOUT'`。

代理、adapter 与其余 axios 字段原样透传 —— `RequestConfig` 就是 `Omit<AxiosRequestConfig, 'url' | 'method' | 'data'>`，非 headers 字段在构造配置时展开（实例级在前，单次调用在后）。

## 四个平台的签名机制

签名器表与默认 judge 在 `client/runtime.ts` 的 `PLATFORM_RUNTIME` 里一次性装配，四个入口共用同一张表。这张表也是签名器名的事实源：每个平台用 `keyof` 从它推出名字联合（如抖音 `'a-bogus' | 'x-bogus'`），`defineXxxEndpoint` 拿来把端点 `sign` 的字符串分支收窄，写错名字编译期即报错 —— 与下面各签名器运行时查表（查不到抛 `未注册的签名器`）是同一份名字的两端。

### 抖音

两个签名器，都先做前置校验再签，且**都以一步 secsdk 收尾**：

- **`a-bogus`**（19 个端点用：17 条声明 `douyinBogus(n)`，外加 `loginQrcode` 的 `[aBogus(), secsdk()]` 与 `mixAweme` 的 `sign: 'a-bogus'`）—— 先校验是绝对 URL，再用 `douyinSign.AB(...)` 签「tail 重排后、a_bogus 之前」的那段 query，结果写进 query 的 `a_bogus`。
- **`x-bogus`**（1 个端点用，`commentReplies`）—— 先校验 pathname 至少 3 段且带 query，再写 query 的 `X-Bogus`。
- **`x-secsdk-web-signature`** —— 不是第三个签名器名，而是复合进上面两个的收尾一步。它与 AB / XB 有三点不同：**改写整条 URL**（签名算的是规范化后的 query，服务端也按收到的 query 校验，所以必须发它返回的那条 URL）、**只对 SDK 策略表里的 path 生效**（14 个 GET / 6 个 POST，表外原样返回）、**必须最后执行**（顺序是 a_bogus / x_bogus → 本签名，前者往 query 里加参数）。`uifid` 从 `ctx.cookie` 的 `UIFID` 取。

<Callout>
  **为什么不注册成第三个签名器名**：`sign` 是单槽位，而 secsdk 对策略表外是无操作 ——
  无条件套用是安全的。另起一个名字只会逼出 `'a-bogus+secsdk'` 这种复合命名。
  影响面上，`music/detail`（`musicInfo`）在策略表内，补上它之前实测 15/15 被
  `Blocked by ArgusSecurityPlugin Uifid Not Found` 拦死；作品详情、用户作品、
  喜欢列表也都在表内。`sign: false` 的端点不经过签名器，它们的 path 也都不在表里。
</Callout>

**签名读的 UA 是 `ctx.userAgent`**，它来自平台基线，且能被调用方的 `headers['user-agent']` 覆盖。这条链断掉的后果很难查：用空 UA 签名，服务端必然拒绝。

另有一个 Referer 注入 helper（`douyin/referer.ts` 的 `withDouyinReferer`），7 个端点的 `build` 调它；调用方已经传了 `referer`（大小写不敏感）时不注入。

### B站

`wbi` 与 `qtparam` 两个签名器共享一个 `WbiSigner`：

- **`wbi`** —— 需要先取 nav 接口拿 key。取 nav 走的是 **`ctx.send(..., 'prepare')`**（不是直连 axios），带 30 分钟 TTL 缓存。签名用 `mixinKeyEncTab` 重排 + md5，产出 `&wts=..&w_rid=..`。
- **`qtparam`** —— cookie 为空时只加 `&platform=html5`；否则复用同一个 nav 结果读 `vipStatus`，VIP 加 `&fnval=4048&fourk=1`，非 VIP 加 `&qn=64&fnval=16`。签名基于**未加 fnval 的原始 URL**。

<Callout type="warn">
  **wbi key 缓存是进程级共享的，不是每实例一份。** `PLATFORM_RUNTIME` 是模块级 `const`，
  `createBilibiliSigners()` 在模块求值时只调用一次，所有 client 实例、静态 fetcher、HTTP 路由
  拿到的是同一个 `WbiSigner`；`sign/steps.ts` 的模块级 `sharedWbi` 也是它，所以端点声明的
  `wbi()` 与 request 层的 `sign: 'wbi'` 共用同一份 key 缓存。这也意味着：两个用不同 cookie 的
  实例会共用同一份 wbi key。
</Callout>

### 小红书

三个签名器（`xhs-post` / `xhs-get` / `xhs-get-trace`）统一注入 `x-s` / `x-s-common` / `x-t`，带 trace 的那个再加 `x-b3-traceid`。签名路径取 `spec.signPath`，缺省取 URL 的 pathname。

`a1` 从 cookie 里**按名精确匹配**取（不是子串匹配 —— 子串匹配曾经是一个真实缺陷）。算法委托同仓内联实现（`sign/xhshow/`）的模块级单例。

`prepare` 用得最多的地方也在这里：小红书**全部 13 个端点**都在 cookie 缺 `a1` 时先打三个请求换游客会话（cookie + SSK）—— 降级由 `defineXiaohongshuEndpoint` 横切注入，端点声明里不逐个写。快手两条 H5 端点也用 `prepare`（did 是纯本地生成的、不出网），另有一条 PC 端点用 `kuaishouPcPrepare`。

### 快手

一个签名器（`hxfalcon`），`live_api`（`/rest/k/*`）与 H5（`/rest/wd/*`）共用 —— 快手两套命名空间的签名算法是同一套，区别只在喂什么料。

签名的三份料全部从 spec 上取：

| 料 | 来源 | 说明 |
| -- | ---- | ---- |
| query | `spec.url` 解析 | 必须含 `caver`（它参与 sign input）。缺了就按签名器自己的 `catVersion` 补，补的值与最终发出的一致 |
| 签名路径 | `spec.signPath` | 与 `url` 的 pathname 不同（`userProfile` 的 12 个分片各有各的 `/rest/k/*` 规范路径） |
| 请求体 | `spec.body` | POST 端点必须参与签名 |

产物写回 URL（`__NS_hxfalcon` + `caver`）与请求头（`kww`）。`kww` 有匿名兜底，**签名从不读 cookie** —— cookie 只影响 `kww` 走登录分支还是匿名分支。

<Callout type="info">
  这里曾经是整个 transport 层最大的断链，两处**同时**漏在 `PLATFORM_RUNTIME.kuaishou`
  上：`signers` 没装（`KuaishouSigner` 写好了却零调用点，于是每个快手请求都不带签名，
  只能拿 cookie 当替代凭证）、`judge` 没装（`kuaishouJudge` 同样零调用点，业务失败全被
  兜底判成成功）。两者都不报编译错误、都不挂测试。现在 `test/client/runtime.test.ts`
  按平台遍历断言「signers 与 judge 都得有，且表里每项都是函数」，把这一类静默漏项钉住。
</Callout>

<Callout type="warn">
  **签名接上了，但 `photo/info` 现在不是快手单个作品的主通道。** 2026-09-05 实测：
  那条接口对 amagi 与对照项目一视同仁地回 `2001 antispam need captcha`，七个变量
  （签名 / 请求头 / did / cookie / 分享页预热 / 真 share 参数 / 数字 photoId）逐个排除
  后都是 2001；而快手自己的 H5 分享页 SSR 用的是**免签的** `ugH5App/photo/simple/info`。
  所以 `kuaishou.videoWork`（`/fetch_one_work`）走的是那条免签接口 —— 它**不声明 `sign`**，
  签名的完整版在 `kuaishou.videoWorkFull`（`/fetch_one_work_full`）。
  验签名到底有没有接上，要拿 `videoWorkFull` 或任一 `live_api` 端点验，别拿 `videoWork`。
</Callout>

### 风控挑战：`PLATFORM_RUNTIME.<平台>.challenge`

`signers` / `judge` 之外的**可选**第三项，四个平台里装了三个：

| 平台 | 提取器 | 信号在哪 |
| ---- | ------ | -------- |
| 快手 | `parseKuaishouCaptcha` | 响应体 |
| 小红书 | `parseXiaohongshuCaptcha` | **只在响应头**（`verifyuuid` / `verifytype`，461 = antiSpider） |
| 抖音 | `parseDouyinCaptcha` | **两条通道，响应头优先**：响应头（`bdturing-verify` / `x-vc-bdturing-parameters`，只认 2xx，body 常为空串）拼不出地址时**兜底读响应体**（滑块中间页 HTML 里的 `verify_data`，**刻意不设状态码闸**）；`jsSdkUrl` / `session` / `verifyData` 只有响应体那条会填 |
| B站 | 无 | — |

`ChallengeExtractor` 的签名是 `(raw, http?)` 而不是 `(raw)`，但两个平台的理由并不相同：小红书的信号**一个字都不在 body 里**（提取器第一个参数就写作 `_raw`，整个函数用不上它）；抖音则是**响应头那条通道优先**，而且要 `http.status` 把那条通道的闸设在 2xx 上 —— 它的 body 里另有一条兜底通道。快手两样都不要，只看 body，不接第二参数也照样装得上。

### 自动解算：`PLATFORM_RUNTIME.<平台>.solveChallenge`

与提取器互补的**可选第六项**，目前只有抖音装了。分界线是**有没有人机判定**：

- **纯工作量证明在管线内解掉并重放。** 抖音 WAF 的 `_wafchallengeid`（sha256 碰撞数）与 VMP 的 `__ac_signature` 由 solver 纯算，返回合并好的完整 cookie 串；`execute` 更新 `ctx.cookie` 并**立即重放**同一请求，`trace.reason` 记 `challenge`（不退避、与业务重试分开）。
- **真人滑块永远返回 `undefined`。** 这类挑战走 `error.challenge` 交给真人；自动重试滑块毫无意义，还会放大风控。

重放有上限（`SOLVE_ROUNDS = 4`）。一次调用里解算成功后 `execute` 会**收口**：不再因为重放结果仍被判可重试而继续退避重试。解不出就把失败信封原样交出去，不吞错。抖音解出的 `__ac_nonce` 还会按 cookie 身份缓存 45 秒，下次裸打页面时直接复用（只存 nonce，签名按当刻时钟重算）。

`runtime/execute.ts` 在 judge 判出 `kind: 'risk'` 时调用**提取器**，结果进失败信封的
`error.challenge`（`{ url, jsSdkUrl?, session?, bizName?, type?, configUrl?, result }`）。
`url` 一律是人能直接打开的验证页：H5 给的是配置接口，会被拼成 `iframe/index.html?…&configUrl=…`
（不用 `mobile/h5/redirect/index.html`，那个跳转壳读的是原字段名 `url` 而不是 `configUrl`，滑块图出不来）。

<Callout type="warn">
  **抖音的地址是照验证中心 SDK 的拼法拼的，头里没有现成的。** 验证头里只有验证参数，没有 URL；
  页面上的渲染层把它们平铺进 query、挂 iframe 到
  `https://rmc.bytedance.com/verifycenter/captcha/v2`，`parseDouyinCaptcha` 照这个拼法交出顶层

## cookie 的完整穿线

```mermaid
flowchart LR
  O["ClientOptions.cookies.&lt;平台&gt;"]
  M["makeClientCtx<br/>ctx.cookie"]
  B["平台基线<br/>headers.delete('cookie')"]
  R["resolveBoundRequest<br/>单次 headers 里的 cookie 覆盖"]
  P["prepare（可选）<br/>换游客 cookie"]
  A["attachCookie<br/>写 Cookie 头"]
  O --> M --> R --> P --> A
  M -.->|刻意不放 cookie| B
```

六个要点：

1. **来源**：实例是 `ClientOptions.cookies.<平台>`；静态形态是方法第二参；bound 形态是工厂第一参。
2. **基线里刻意不放 cookie**：`makeClientCtx` 拿到平台 config 后立刻 `headers.delete('cookie')`。否则单次调用的 cookie 覆盖会被实例头里的旧值遮蔽。
3. **单次覆盖**：从合并后的 headers 里大小写不敏感地取 `cookie`，取到就替换本次的 `ctx.cookie`。
4. **注入只在一处**：`execute` 的 `attachCookie`，send 之前。
5. **执行期可换**：`prepare` 返回的 `cookie` 会覆盖 ctx，换完的值经 `attachCookie` 生效。
6. **响应侧不回写**：`RawResponse.setCookie` 保留原始数组，但**不会**被写回 `ctx.cookie`。主管线里没有 cookie 自动刷新或轮转 —— 唯一的例外是抖音 passport 自带的 cookie jar 与小红书游客 cookie 的一次性生成。

cookie 解析全仓只有一份实现（`contracts/cookie.ts`）：大小写敏感、以第一个 `=` 分割、不做 URL 解码。

## 两个写了但没人读的字段

`RequestSpec` 上有两个字段，契约注释描述了用途，但通路不存在：

| 字段 | 注释说 | 实际 |
| ---- | ------ | ---- |
| `tag` | 会进 trace | trace 的类型里没有 `tag`。唯一写入点是抖音弹幕端点，无读取点 |
| `extra` | 透传给 sign / decode | `decode(raw, res)` 的签名拿不到 spec。唯一写入点是 B站 `qtparam` 写的 `isvip`，无读取点 |

写代码时不要依赖这两个字段传值。
