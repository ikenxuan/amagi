# 为什么签名需要被验证

抖音的签名算法里藏着若干个**常量**：盐值、`page_id`、`aid`、SDK 版本块、环境字节。
它们会随抖音更新 `bdms.js` 而变，而变的时候**没有任何通知**。

麻烦在于，抖音对签名是**抽样校验**的：

<Callout type="warn" title="一次成功的请求，证明不了任何事">
  签名用错了常量，请求大部分时候照样成功，只是被判定为高风险的概率上升。
  它不报错、不返回空、不给你任何可分辨的信封 —— 表现为「偶尔不稳」，
  而不是「坏了」。所以把「接口能通」当作签名正确的证据，是无效推理。
</Callout>

## 自证模型的三个空转

在这套约束下，常见的测试写法一个都发现不了常量过期：

| 写法 | 为什么无效 |
|---|---|
| 自生成快照 | 首次运行时由**被测代码自己**写入。常量改了，快照跟着改，测试永远绿 |
| 与被测对象比自身 | `expect(v7).toBe(v6)` —— 但两个符号 import 的是同一个模块，等于把函数和自己比 |
| 「输出长度 > 100」这类形状断言 | 错的盐值产出的签名与对的**形状完全一致**，只是字节不同 |

一句话：**没有任何自证型断言能证伪一个常量。** 这不是写得不够好，是模型的问题 ——
缺少一个不随被测代码变化的外部锚点。

## 一个真实的例子

`packages/core` 里数据接口那份 `a_bogus` 曾经用盐值 `cus`，而真实值是 `dhzx`。

它来自 2024-08 一份公开流传的片段，此后再没被算法层面的改动碰过（之后的提交都是
格式化、改目录名、`原样搬迁`）。同一个仓库里 2026-09 新写的 passport 版本用的却是
`dhzx` —— 也就是说**正确的值一直就在旁边**，但没有任何测试能把这件事暴露出来。

它是被这样发现的：拿一份真实浏览器产出的 `a_bogus`，把两个候选盐值分别代进摘要，
看哪个能重现签名里封住的三个字节。

```
query       observed=(19, 103, 137)   dhzx_predicted=(19, 103, 137)   MATCH
query       observed=(19, 103, 137)   cus_predicted=(105, 123, 88)    MISMATCH
```

这正是[验证工具](/docs/v7/dev/sign-verify/tool)做的事。

## 「解码」在这里诚实地指三件事

把这三件事混为一谈，是这类工具开始撒谎的方式。`@ikenxuan/amagi/signing` 导出的每个字段
都携带自己属于哪一类：

<Cards>
  <Card title="① 可还原（plain / time）">
    值就在载荷里，能原样取回：时钟、`aid`、`page_id`、屏幕几何串、版本块、调用计数。
    **没有任何推断。**
  </Card>
  <Card title="② 被绑定但不可还原（digest）">
    载荷里带着某个东西的摘要 —— 三条链各三个 SM3 字节。输入无法从摘要倒推出来，
    所以工具**从不假装能**。它做的是校验：给一个候选值，回答它是不是签名封住的那一个。
    「我的请求被拒了」因此变成「我发的签名是对着另一条 URL 算的」。
  </Card>
  <Card title="③ 根本没被计算（opaque）">
    `msToken` 与访客令牌由平台签发或随机抽出，底下没有明文可找。
    说出这一点就是答案，而不是「没能给出答案」。
  </Card>
</Cards>

## 三个字节够用吗

够 —— 但要说明证据量，而不是藏起来。

`a_bogus` 每条链只有 **24 位**（三个字节）。这不足以把哈希倒推回去，但足以在实战中
判定「某个候选 query 是不是这份签名封住的那一条」：随机命中的概率是 2⁻²⁴，
而误判的代价只是「你以为签名对了」。工具把 `bits` 一并显示出来，就是为了让这个
权衡是可见的，而不是隐含的。

## 为什么还需要结构检查

摘要链只能校验**你提供了候选值的那些输入**。如果一份签名根本不是这套算法产出的，
摘要链会全部报「对不上」——但那可能是因为你给的 query 错了，也可能是因为这压根不是
一个 `a_bogus`。两者要分开。

`structureError()` 做的就是这件事：它重新跑一遍算法固定下来的全部约束 ——
header 魔数、SDK 版本块、声明的长度是否恰好覆盖载荷、以及**内部校验和**。

最后一条是真正有价值的那条。校验和覆盖版本块与五十个标量，而这些字段本身就在载荷里，
所以一份能通过校验和的签名，必然是由一个在**整套布局**上与我们一致的实现装配出来的
——版本块、五十槽置换、噪声展开、以及那个非标准 RC4 密码。不是真算法，凑不出一个。

<Callout type="info" title="刻意不检查长度">
  签名长度跟着屏幕几何串走，两个都对但屏幕不同的浏览器就是会不一样。
  检查长度会把正确的实现判成错的。
</Callout>
